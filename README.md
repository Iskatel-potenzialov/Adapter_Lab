# Qwen LoRA Fine-tuning & Evaluation Studio

Локальная веб-студия для подготовки датасетов, обучения LoRA-адаптеров и проверки того, действительно ли дообучение улучшило модель.

Проект построен вокруг `Qwen2.5-VL-7B-Instruct`. В версии v1 используется только текстовая часть модели.

Главная задача Studio — провести модель через полный и воспроизводимый цикл:

```text
Dataset (датасет) → Validation (проверка) → Split (разделение) → Training (обучение) → LoRA Adapter (адаптер) → Inference (получение ответа) → Base vs LoRA Evaluation (сравнение качества)
```


Studio нужна не только для того, чтобы «обучить LoRA», но и для того, чтобы ответить на более важный вопрос: **чему именно модель научилась и стала ли она лучше на данных, которых не видела во время обучения**.

---

## Studio умеет:

Пользователь может:

- загрузить один полный JSONL-датасет и автоматически разделить его на Train (обучающую выборку) / Validation (проверочную выборку) / Test (тестовую выборку);
- загрузить заранее подготовленные Train / Validation / Test без перемешивания;
- проверить структуру данных до запуска обучения;
- обучить QLoRA-адаптер (LoRA с 4-битной загрузкой базовой модели для экономии видеопамяти) на локальной NVIDIA GPU;
- следить за loss (ошибкой модели) и validation metrics (метриками на проверочной выборке);
- сохранить лучший checkpoint (промежуточное состояние модели с лучшим результатом на Validation);
- протестировать Base model (исходную модель без LoRA) и модель с LoRA;
- автоматически сравнить Base и LoRA на одном и том же Test;
- проверить JSON, отдельные поля и полное совпадение ответа с эталоном;
- дополнительно выполнить LLM Judge (оценку ответов другой языковой моделью);
- скачать готовый LoRA-адаптер отдельно от training checkpoints (промежуточных файлов обучения).

---

## Основная идея проекта

Не пытаться сделать универсальную платформу «на все случаи жизни». Вместо этого Studio построена вокруг стабильного жизненного цикла модели:

```text
Input → Dataset → Validation → Split → Training → Adapter → Inference → Evaluation
```

На каждом этапе допускаются разные стратегии, но общий контракт остаётся одинаковым.

Например:

- Dataset (датасет) можно загрузить одним файлом или готовыми Train / Validation / Test;
- Split (разделение данных) может быть автоматическим или заранее заданным;
- Evaluation (оценка) может быть строгой детерминированной проверкой или дополнительной семантической оценкой через LLM Judge;
- задача может требовать обычного текста или структурированного JSON.

Такой подход позволяет расширять Studio постепенно, не перестраивая приложение под каждый новый датасет.

## Архитектура

```text
Windows
Browser
    │
    │ HTTP
    ▼
Ubuntu
├── Vite / React + TypeScript frontend :5173
│
├── FastAPI backend :8000
│   ├── datasets
│   ├── Inference
│   ├── Evaluation
│   └── train.py — отдельный процесс обучения
│
└── Qwen2.5-VL-7B-Instruct
    + QLoRA adapters
    + NVIDIA GPU
```

Frontend и backend Aurora Studio запускаются на Ubuntu-машине.

Пользователь открывает интерфейс с Windows-компьютера в обычном браузере по IP-адресу Ubuntu в локальной сети.

Браузер получает React-интерфейс от Vite по HTTP. После загрузки frontend взаимодействует с FastAPI backend через HTTP REST API с помощью `fetch`.

Для длительных операций, таких как Training и Evaluation, frontend использует polling (периодический опрос): через определённый интервал повторно запрашивает состояние задачи у backend.


## Обучение запускается отдельным процессом

FastAPI не обучает модель внутри HTTP-запроса.

Backend создаёт training job (задачу обучения), формирует конфигурацию и запускает отдельный `backend/train.py` subprocess (дочерний процесс).

Это сделано потому, что обучение:

- может идти долго;
- активно использует GPU;
- может завершиться CUDA/OOM-ошибкой (ошибкой GPU или нехваткой видеопамяти);
- должно иметь собственные логи, checkpoints и код завершения.

Если процесс обучения завершился некорректно, Studio не помечает такую задачу как успешно завершённую.

---

## Работа с GPU

Целевая машина проекта — NVIDIA GeForce RTX 3060 с 12 GB VRAM (видеопамяти).

Training (обучение), Inference (генерация ответов) и Evaluation (оценка) не используют GPU одновременно.

Перед тяжёлой операцией ненужная модель выгружается из памяти. Это простой способ избежать конфликтов за VRAM без отдельного сервиса распределения ресурсов.

## Датасеты: два режима

### 1. Automatic split (автоматическое разделение)

Пользователь загружает один JSONL-файл, после чего Studio создаёт Train / Validation / Test.

По умолчанию используются пропорции:

```text
80% Train
10% Validation
10% Test
```

Если в примерах есть `group_id` (идентификатор группы связанных примеров), Studio разделяет данные целыми группами.

Это важно, если несколько строк являются вариантами одного и того же исходного объекта. Они не должны одновременно попасть в Train и Test, иначе возникает data leakage (утечка информации из обучения в тест).

### 2. Predefined split (заранее подготовленное разделение)

Можно сразу загрузить три файла:

```text
train.jsonl
validation.jsonl
test.jsonl
```

В этом режиме:

- `group_id` обязателен;
- одна группа не может одновременно находиться в разных split (частях выборки);
- Studio не перемешивает пользовательские файлы;
- для каждой части сохраняются количество строк, количество групп и hash (контрольная сумма содержимого).

Этот режим нужен, когда Test должен быть действительно независимым: например, содержать новые бизнес-кейсы, новые домены или данные из другого периода времени.



Пример для датасета "обращения граждан" (структурированный JSON-ответ)
Одна строка датасета:


```json
{
  "task_profile": "structured_json",
  "group_id": "electricity_004",
  "evaluator": "json",
  "messages": [
    {
      "role": "system",
      "content": "Определи тему обращения: electricity=электричество/освещение, cleanliness=мусор/уборка, heating=отопление, water_supply=водоснабжение, other=иная ясная тема, unknown=неясная тема или две равнозначные темы разных категорий. Учитывай главную проблему, не контекст и следствия. confidence: high=тема прямо следует из текста; medium=тема наиболее вероятна по косвенным признакам; low=для unknown.     },
    {
      "role": "user",
      "content": "Почему как вечер, так сеть проседает? Нормально приборы не включить!"
    },

      "role": "assistant",
      "content": "{\"category\":\"electricity\",\"confidence\":\"high\"}"

```

## Structured JSON evaluation (оценка структурированного JSON)

Для задач со структурированным JSON одной метрики недостаточно.

Studio отдельно проверяет несколько уровней качества:

| Metric | Что означает |
|---|---|
| **JSON validity** | Получился ли корректный JSON, который вообще можно разобрать программно. |
| **Exact full-record accuracy** | Совпал ли весь JSON целиком со всеми ожидаемыми полями и значениями. |
| **Field accuracy** | Какая доля отдельных полей заполнена правильно. |
| **Per-field accuracy** | Насколько хорошо модель работает с каждым конкретным полем. |

### Safe JSON normalization

Safe JSON normalization (безопасная нормализация JSON) нужна для того, чтобы не штрафовать модель за внешнюю «обёртку», если сам JSON корректен.

Например, Studio может убрать:

```text
JSON:
{...}
```

или Markdown-блок вокруг одного валидного JSON.

При этом Studio **не исправляет ошибки внутри JSON**:

```text
{a: 1}
{'a': 1}
{"a": 1,}
```

не превращаются автоматически в правильный ответ.

Принцип простой:

> Можно убрать внешний шум, но нельзя «додумывать» или ремонтировать ответ модели вместо неё.

Исходный ответ модели при этом всегда сохраняется отдельно.

## LLM Judge (оценка ответов языковой моделью)

Кроме строгой проверки, Studio использует LLM Judge (языковую модель в роли дополнительного оценщика).

Judge получает:

- исходный запрос;
- эталонный ответ;
- два анонимных ответа `Answer A` и `Answer B`.

Он не знает, где Base, а где LoRA. Это blind A/B evaluation (слепое сравнение двух вариантов), которое уменьшает риск предвзятой оценки.

Judge оценивает:

- `correctness` (насколько ответ корректен по смыслу);
- `completeness` (насколько ответ полный);
- `format` (насколько хорошо соблюдён формат).

LLM Judge используется **как дополнительная семантическая оценка**, а не вместо строгих JSON-метрик.

## Обучение

<img width="1132" height="553" alt="image" src="https://github.com/user-attachments/assets/403414be-5be3-4d2b-8324-d2d5a981cdbb" />


Aurora Studio использует **QLoRA** — режим дообучения, при котором базовая модель загружается в квантованном 4-битном виде, а ее основные веса не изменяются.

Вместо полного переобучения модели к части линейных слоев Transformer подключаются небольшие обучаемые модули **LoRA**.

Обычно LoRA добавляется к слоям attention:

```text
q_proj
k_proj
v_proj
o_proj
```

а при соответствующей конфигурации — также к MLP-слоям:

```text
gate_proj
up_proj
down_proj
```

LoRA не заменяет исходные слои модели. Она добавляет к их результату небольшую обучаемую корректировку.


Таким образом, при запуске обучения Studio:

```text
загружает Base model в 4-bit
        ↓
замораживает ее основные веса
        ↓
подключает LoRA к выбранным слоям
        ↓
обучает только параметры LoRA
```

Во время inference запрос по-прежнему проходит через базовую модель, но в слоях с LoRA к обычному результату добавляется обученная корректировка.

После обучения Studio сохраняет не полную копию модели, а только **LoRA-адаптер** и его конфигурацию.

### Настройки обучения

Перед запуском обучения Aurora Studio позволяет использовать рекомендуемую конфигурацию или изменить параметры вручную в режиме Custom.
Основные настройки:
* **epochs (количество эпох)** — сколько полных проходов модель делает по Train-датасету; влияет на длительность обучения и степень адаптации модели к данным.
* **batch_size (размер обучающего batch)** — сколько примеров обрабатывается одновременно; влияет прежде всего на расход VRAM.
* **eval_batch_size (размер batch при Validation)** — сколько примеров одновременно используется при проверке модели; влияет на расход VRAM во время evaluation.
* **grad_accum (накопление градиентов)** — позволяет имитировать больший batch без увеличения количества одновременно загружаемых примеров; влияет на effective batch size.
* **learning_rate (скорость обучения)** — определяет величину изменения обучаемых весов на каждом шаге; слишком большое значение может сделать обучение нестабильным, слишком маленькое — замедлить его.
* **lr_scheduler_type (схема изменения learning rate)** — задает, как скорость обучения меняется в процессе обучения.
* **warmup_ratio (доля разогрева)** — определяет начальную часть обучения, в течение которой learning rate постепенно увеличивается.
* **lora_r (ранг LoRA)** — определяет размер обучаемых матриц LoRA; влияет на количество обучаемых параметров, потребление памяти и емкость адаптера.
* **lora_alpha (масштаб LoRA)** — регулирует силу влияния LoRA-коррекции на базовую модель.
* **lora_dropout (dropout LoRA)** — случайно отключает часть LoRA-связей во время обучения и используется для снижения переобучения.
* **target_modules (целевые слои)** — определяет, к каким слоям модели подключается LoRA, например q_proj, k_proj, v_proj, o_proj.
* **max_seq_length (максимальная длина последовательности)** — ограничивает количество токенов в одном примере; влияет на возможность сохранить длинные примеры целиком и на расход VRAM.
* **early_stopping_patience (допустимое число проверок без улучшения)** — позволяет автоматически остановить обучение, если качество на Validation перестало улучшаться.
* **early_stopping_threshold (минимальное улучшение)** — задает, насколько должен уменьшиться eval_loss, чтобы результат считался улучшением.

### Validation и best checkpoint

Во время обучения Studio считает `eval_loss` (ошибку на Validation) и сохраняет best checkpoint (лучшую контрольную точку).

Также поддерживается early stopping (ранняя остановка): обучение можно остановить, если Validation больше не улучшается.

# Практический кейс №1: извлечение и структурирование требований системного аналитика

## Постановка задачи

Для проверки Qwen LoRA Fine-tuning & Evaluation Studio была выбрана задача автоматизации части работы системного аналитика.

Модель получает неструктурированный запрос заказчика и должна преобразовать его в формализованный набор требований к информационной системе, распределив информацию по шести смысловым категориям.

Результат возвращается в фиксированной JSON-схеме:

```
{
  "functional_requirements": [],
  "non_functional_requirements": [],
  "ui_requirements": [],
  "security_requirements": [],
  "audit_requirements": [],
  "acceptance_criteria": []
}
```

**Назначение полей JSON:**

| Поле                          | Значение                                                                   |
| ----------------------------- | -------------------------------------------------------------------------- |
| `functional_requirements`     | Функциональные требования — что система должна делать                      |
| `non_functional_requirements` | Нефункциональные требования — производительность, надёжность и ограничения |
| `ui_requirements`             | Требования к пользовательскому интерфейсу                                  |
| `security_requirements`       | Требования безопасности — авторизация, доступ, защита данных               |
| `audit_requirements`          | Требования к журналированию действий и событий                             |
| `acceptance_criteria`         | Критерии приёмки — проверяемые условия выполнения требований               |

Модель должна использовать только информацию из исходного запроса, не придумывать отсутствующие требования и оставлять соответствующие массивы пустыми, если нужных сведений нет.

## Конструирование датасета

Был подготовлен синтетический датасет из **500 примеров, объединённых в 100 бизнес-сценариев**.

Каждый сценарий описывал конкретную бизнес-ситуацию с заранее определённым набором требований. На его основе создавались пять языковых вариантов с одинаковым смыслом, но разной формой подачи: краткая постановка задачи, устное обсуждение, протокол встречи, сырой запрос и прямое перечисление.

Цель — научить модель извлекать одни и те же требования из формальных, разговорных и плохо структурированных текстов.

### Разделение данных

| Выборка    | Примеры | Бизнес-сценарии |
| ---------- | ------- | --------------- |
| Train      | 400     | 80              |
| Validation | 50      | 10              |
| Test       | 50      | 10              |
| **Всего**  | **500** | **100**         |

Для связанных формулировок использовался `group_id` — идентификатор бизнес-сценария.

Все пять вариантов одного сценария оставались внутри одной выборки. Благодаря этому модель не обучалась на одной формулировке задачи с последующей проверкой на практически идентичной.

**Test содержал новые бизнес-сценарии, не использовавшиеся при обучении.**

### Пример сценарного конструирования

**Группа:** `manufacturing__auth` — авторизация, SSO и блокировка учётной записи.

**Суть сценария:** вход через корпоративный SSO и пропуск сотрудника, привязка к существующему аккаунту по табельному номеру без дублирования, блокировка на 15 минут после пяти неудачных попыток входа, регистрация событий безопасности.

Пример двух вариантов из пяти.

**Вариант 1. Протокол встречи**

> Со встречи с заказчиком:
>
> - Хотим вход для пользователей через корпоративный SSO и вход по пропуску сотрудника.
> - Если человек уже есть в системе, новый профиль создавать нельзя — надо привязать вход к существующему аккаунту по табельному номеру.
> - После пяти неудачных попыток входа парольным способом аккаунт нужно блокировать на 15 минут.
> - В журнале безопасности хотим видеть успешные входы и блокировки.

**Вариант 2. Сырой запрос**

> Запрос от бизнеса, формулировки пока сырые. В журнале безопасности хотим видеть успешные входы и блокировки. Хотим вход для пользователей через корпоративный SSO и вход по пропуску сотрудника. Если человек уже есть в системе, новый профиль создавать нельзя — надо привязать вход к существующему аккаунту по табельному номеру. После пяти неудачных попыток входа парольным способом аккаунт нужно блокировать на 15 минут.

Для этой же группы были подготовлены ещё три варианта: краткая постановка задачи, устное обсуждение и прямое перечисление требований.

Во всех случаях целевой JSON оставался одинаковым — менялась только форма исходного сообщения.

## Обучение и выявленные сложности

На подготовленном датасете был проведён **один цикл QLoRA-обучения** с последующим сравнением базовой модели (Base) и модели с LoRA-адаптером.

Главная сложность заключалась не в генерации корректного JSON, а в **смысловом разграничении требований**.

Исходная модель уже выдавала валидный JSON в 100% случаев, но допускала ошибки при распределении информации между полями.

Например, Base могла:

- отнести ограничение «обработка должна занимать не более 2 минут» к функциональным требованиям вместо нефункциональных;
- поместить требование об отображении прогресса выполнения в критерии приёмки вместо UI;
- отнести блокировку пользователя после неудачных попыток входа к общим ограничениям вместо Security;
- оставить Audit пустым, хотя заказчик прямо требовал журналирование действий.

Модель понимала общий смысл запроса, но недостаточно стабильно следовала заданной методике классификации.

После QLoRA-обучения адаптер стал значительно точнее определять, какие сведения относятся к Functional, Non-functional, UI, Security, Audit и Acceptance Criteria.

Таким образом, дообучение улучшило **не форматирование ответа, а способность структурировать требования по смысловым категориям**.



## Оценка качества

Сравнение Base и LoRA проводилось на одинаковом Test из **50 новых бизнес-примеров**.

Studio проверяла валидность JSON, полное совпадение записи с эталоном, точность отдельных полей и дополнительную семантическую оценку через LLM Judge.

### Результаты Base vs LoRA

| Метрика                  | Что показывает                        | Base    | LoRA        |
| ------------------------ | ------------------------------------- | ------- | ----------- |
| **Accuracy**             | Доля полностью правильных результатов | 0,00%   | **72,00%**  |
| **JSON validity**        | Корректность JSON                     | 100,00% | 100,00%     |
| **Full record accuracy** | Совпадение всех шести полей           | 0,00%   | **72,00%**  |
| **Field accuracy**       | Точность отдельных полей              | 34,33%  | **92,00%**  |
| **LLM Judge score**      | Общая семантическая оценка            | 86,06%  | **92,24%**  |
| **Pass rate**            | Доля ответов, принятых LLM Judge      | 98,00%  | **100,00%** |
| **Correctness**          | Смысловая корректность                | 85,28%  | **92,58%**  |
| **Completeness**         | Полнота извлечённых требований        | 86,18%  | **92,18%**  |
| **Format**               | Соблюдение структуры ответа           | 88,98%  | **90,98%**  |

**Почему у Base Accuracy = 0%, хотя Field accuracy = 34,33%?**

`Full record accuracy` — строгая метрика: если хотя бы одно из шести полей отличается от эталона, весь пример считается неправильным.

Base правильно заполняла отдельные поля, но ни в одном из 50 примеров не совпали сразу все шесть.

После обучения LoRA полностью правильно обработала **36 из 50 тестовых примеров**, достигнув Exact accuracy 72%.

### Точность по отдельным категориям

| Поле                          | Base | LoRA     |
| ----------------------------- | ---- | -------- |
| `functional_requirements`     | 0%   | **80%**  |
| `non_functional_requirements` | 26%  | **90%**  |
| `ui_requirements`             | 50%  | **100%** |
| `security_requirements`       | 70%  | **100%** |
| `audit_requirements`          | 60%  | **100%** |
| `acceptance_criteria`         | 0%   | **82%**  |

Наиболее заметные улучшения получены для требований к интерфейсу, безопасности и аудиту — **100% точности на Test** после обучения.

Точность функциональных требований выросла с 0% до 80%, нефункциональных — с 26% до 90%, критериев приёмки — с 0% до 82%.

## Вывод по эксперименту

Один цикл QLoRA-обучения позволил адаптировать модель к конкретной методике системного анализа: извлекать требования из неструктурированного текста, относить их к нужным категориям и представлять в фиксированной JSON-схеме.

**Основные результаты:**

- Exact full-record accuracy: **0% → 72%**.
- Field accuracy: **34,33% → 92%**.
- JSON validity: **100% → 100%**.

Неизменная валидность JSON подтверждает, что главное улучшение связано с качеством структурирования содержания, а не с освоением синтаксиса.

Кейс демонстрирует завершённый цикл: **сценарное конструирование датасета → разделение Train/Validation/Test → QLoRA-обучение → сравнение Base и LoRA на новых бизнес-сценариях**.

# Практический кейс №2: классификация обращений граждан

## Постановка задачи

Во втором эксперименте решалась задача автоматической классификации текстовых обращений граждан.

Цель — дообучить `Qwen2.5-VL-7B-Instruct` определять **основную тему обращения и степень определённости классификации**, возвращая результат в фиксированном JSON-формате.

Модель должна выбирать одну категорию:

| Значение `category` | Значение                                                           |
| ------------------- | ------------------------------------------------------------------ |
| `electricity`       | Электричество, электроснабжение, освещение                         |
| `cleanliness`       | Мусор, загрязнения, уборка                                         |
| `heating`           | Отопление                                                          |
| `water_supply`      | Водоснабжение                                                      |
| `other`             | Другая, но понятная тема                                           |
| `unknown`           | Неопределённая тема или две равнозначные проблемы разных категорий |

Дополнительное поле `confidence` определяет уровень уверенности по правилам задачи:

| Значение | Правило                                                          |
| -------- | ---------------------------------------------------------------- |
| `high`   | Тема прямо следует из текста                                     |
| `medium` | Тема наиболее вероятна по косвенным признакам                    |
| `low`    | Однозначная классификация невозможна; используется для `unknown` |

Пример результата:

```
{
  "category": "electricity",
  "confidence": "medium"
}
```

Основная сложность — модель должна учитывать **главную проблему, а не отдельные слова, контекст или последствия**.

Например, жалоба на повторное списание денег за абонемент в бассейн относится к `other`, а не к `water_supply`. Аналогично холод в помещении может указывать на отопление лишь косвенно.

Если обращение содержит две равнозначные проблемы разных категорий, модель должна возвращать `unknown/low`, а не произвольно выбирать одну из них.

## Конструирование датасета

Был подготовлен **синтетический датасет с эталонной разметкой**, основанный на сценарном конструировании.

Сначала определялись ситуация, правило классификации и ожидаемый JSON-ответ. Затем создавались несколько естественных формулировок одного обращения.

Это позволяло контролировать не только объём данных, но и конкретные правила, которым обучалась модель.

### Типы сценариев

**1. Прямые признаки — `high`**

Тема очевидна из текста: отсутствует электричество, не убирается мусор, неисправно отопление или нарушена подача воды.

Модель должна правильно определить категорию и не занижать уровень определённости.

**2. Косвенные признаки — `medium`**

Описаны симптомы, но причина прямо не названа. Например, зимой в помещении постоянно холодно при закрытых окнах или несколько приборов одновременно теряют настройки.

Задача — выбрать наиболее вероятную категорию, не выдавая предположение за прямой факт.

**3. Неопределённые и конфликтующие темы — `unknown/low`**

Информации недостаточно либо описаны две равнозначные проблемы разных категорий.

Модель должна отказаться от произвольного выбора темы и следовать правилу `unknown/low`.

### Группировка и разделение

Для каждой ситуации создавались связанные формулировки, объединённые через `group_id`.

Разделение Train / Validation / Test выполнялось целыми группами, чтобы языковые варианты одного сценария не попадали одновременно в обучение и тестирование.

Использовался режим **Predefined Split** — заранее подготовленные выборки без дополнительного перемешивания Studio.

Это позволяло воспроизводить эксперименты и сравнивать адаптеры на одинаковых данных.

## Итеративное обучение и выявленные сложности

В отличие от первого кейса, здесь было проведено **три последовательные итерации QLoRA-обучения** с анализом ошибок и корректировкой датасета.

Цель состояла не в механическом увеличении количества примеров, а в улучшении конкретных правил классификации.

### v1 — первоначальное обучение

Первый Train содержал **480 примеров**.

После обучения модель соблюдала JSON-схему, но допускала смысловые ошибки:

- путала `high` и `medium`;
- выбирала категорию при двух равнозначных проблемах вместо `unknown`;
- недостаточно стабильно различала прямые и косвенные признаки;
- иногда ориентировалась на второстепенный контекст.

На исходном Test точность полного совпадения JSON составила **73,33%**.

### v2 — корректировка разметки и правил

Анализ ошибок показал, что часть проблем была связана не только с моделью, но и с **противоречиями в эталонной разметке**.

Похожие обращения иногда получали разные значения `confidence`, хотя должны были обрабатываться по одному правилу.

Были пересмотрены спорные метки и добавлены примеры для косвенных признаков и многотемных обращений.

Train увеличился до **670 примеров**, Exact accuracy после повторного обучения — до **84,17%**.

### v3 — контрастивные примеры

Третья итерация была направлена на ошибки, оставшиеся после v2.

В Train добавили **80 целевых контрастивных примеров**, увеличив обучающую выборку до 750 строк.

Контрастивный подход заключался в создании похожих по словам и контексту ситуаций, требующих разных ответов.

Например:

- явная неисправность отопления — `heating/high`, косвенные признаки холода — `heating/medium`;
- жалоба на уборку классифицируется по основной проблеме, даже если присутствует посторонний контекст;
- две равнозначные темы разных категорий — `unknown/low`;
- упоминание объекта, связанного с водой или электричеством, само по себе не определяет категорию.

Таким образом, каждое изменение датасета было связано с конкретной ошибкой или гипотезой её исправления.

### Методика улучшения

Эксперимент проводился по повторяемому циклу:

**Обучение → Evaluation → анализ ошибок → гипотеза → корректировка датасета → повторное обучение.**

Анализировались не только итоговые метрики, но и конкретные случаи, когда модель:

- неправильно определила основную категорию;
- верно выбрала категорию, но ошиблась в `confidence`;
- следовала второстепенному контексту;
- ошибалась из-за неоднозначности самого обращения или противоречивого эталона.

Такой подход позволил улучшать модель через **управляемое конструирование данных**, а не только настройку параметров обучения.

## Оценка качества

Для сравнения использовались детерминированная генерация и строгие метрики структурированного JSON.

Главная метрика — **Exact full-record accuracy**: доля обращений, где оба поля (`category` и `confidence`) полностью совпадают с эталоном.

Дополнительно проверялись точность категории, точность уровня определённости и отдельные ошибки.

### Результаты трёх итераций

Все три версии оценивались на прежнем общем Test из 120 обращений.

| Версия  | Train | Exact accuracy |
| ------- | ----- | -------------- |
| LoRA v1 | 480   | 73,33%         |
| LoRA v2 | 670   | 84,17%         |
| LoRA v3 | 750   | **92,50%**     |

Для v3 на этом Test точность отдельных полей составила:

- `category` — **97,50%**;
- `confidence` — **93,33%**.

В эксперименте с v3 исходная Base показала 56,67% Exact accuracy, модель с LoRA — 92,50%.

Результаты подтвердили улучшение на прежней тестовой выборке. Однако её ошибки использовались при разработке новых версий датасета, поэтому возник риск подстройки под Test.

Для проверки обобщающей способности потребовался отдельный контрольный набор.

## Контроль переобучения и независимая проверка

Контроль качества включал разделение Train / Validation / Test, отслеживание ошибок обучения и Validation, выбор лучшего checkpoint, а также проверку готовых адаптеров на отдельной тестовой выборке.

Поскольку прежний Test использовался для анализа ошибок, был дополнительно подготовлен **новый синтетический Test из 120 обращений — 24 сценария по пять формулировок**.

Эти сценарии не участвовали в обучении и предыдущем анализе ошибок. Перед запуском Evaluation проверялась эталонная разметка.

Состав контрольной выборки:

| Тип           | Количество |
| ------------- | ---------- |
| `high`        | 80         |
| `medium`      | 20         |
| `unknown/low` | 20         |
| **Всего**     | **120**    |

Готовые адаптеры v2 и v3 оценивались на одинаковом Test, **без повторного обучения**, с одинаковыми настройками генерации.

### Результаты на новом Test

| Метрика                   | Base   | LoRA v2    | LoRA v3    |
| ------------------------- | ------ | ---------- | ---------- |
| **Exact accuracy**        | 56,67% | 93,33%     | **95,83%** |
| **Точность `category`**   | 85,83% | **98,33%** | 95,83%     |
| **Точность `confidence`** | 58,33% | 93,33%     | **98,33%** |
| **Field accuracy**        | 72,08% | 95,83%     | **97,08%** |
| **JSON validity**         | 100%   | 100%       | 100%       |

Количество полностью правильных ответов:

- Base — **68 из 120**.
- LoRA v2 — **112 из 120**.
- LoRA v3 — **115 из 120**.

На новом Test v3 улучшила Exact accuracy относительно v2 на **2,5 процентного пункта**, сохранив преимущество на ранее не использованных сценариях.

При этом улучшения оказались неравномерными: v3 лучше определяла `confidence` (98,33% против 93,33%), но немного уступила v2 по точности самой категории (95,83% против 98,33%).

### Анализ ошибок и регрессий

Сопоставление ответов двух адаптеров показало:

- **5 ошибок v2 были исправлены в v3**;
- **2 новые ошибки появились в v3**;
- **3 ошибки остались у обеих версий**.

Основная часть исправлений касалась уровня определённости: v2 нередко возвращала `medium` для достаточно очевидных проблем, связанных с повреждённым кабелем, загрязнениями или отоплением.

Новые ошибки v3 относились уже к определению категории. Например, модель не распознала одну из санитарных ситуаций и ошибочно отнесла финансовую жалобу на абонемент в бассейн к водоснабжению.

Это показало, что **улучшение одного аспекта классификации не гарантирует отсутствия регрессий в другом**. Поэтому оценка должна включать не только общую точность, но и анализ конкретных ответов.

### Роль LLM Judge

Дополнительно использовался LLM Judge для семантической оценки ответов. Однако в задаче с двумя строго определёнными полями он оказался менее чувствительным к некоторым различиям, например между `high` и `medium`.

Поэтому основными показателями качества оставались **Exact accuracy, точность `category` и `confidence`, а также анализ ошибок и регрессий**. LLM Judge использовался только как дополнительный инструмент.

## Вывод по эксперименту

Эксперимент показал, что качество QLoRA-дообучения зависит не только от гиперпараметров, но и от **согласованности разметки, структуры датасета и методики анализа ошибок**.

В рамках кейса были проведены три итерации обучения, применены сценарное и контрастивное конструирование данных, исправлены противоречия в разметке и выполнена проверка на новом контрольном Test.

**Основные результаты:**

- Прогресс v1 → v2 → v3 на прежнем Test: **73,33% → 84,17% → 92,50%**.
- На новом Test: **56,67% Base → 93,33% LoRA v2 → 95,83% LoRA v3**.
- Зафиксированы как улучшения, так и регрессии между версиями адаптеров.

При этом контрольный набор оставался синтетическим и содержал несколько формулировок каждого сценария. Полученные показатели характеризуют качество модели на подготовленных тестовых ситуациях, а не на реальном потоке обращений.

Главный результат кейса — **переход от разового fine-tuning к управляемому итеративному процессу улучшения LLM**, где изменения датасета основаны на конкретных ошибках, а их эффективность проверяется измеримыми метриками.

```text
POST /training/start
GET  /training
GET  /training/{job_id}
```

### Inference API

```text
GET  /inference/status
POST /inference/generate
```

### Evaluation API

```text
POST /evaluations
GET  /evaluations
GET  /evaluations/{evaluation_id}
GET  /evaluations/{evaluation_id}/results
```

### Adapter API

```text
GET    /adapters
GET    /adapters/{adapter_id}
DELETE /adapters/{adapter_id}
```

## Offline mode (работа без обращения к внешнему сервису модели)

Модель загружается локально и не требует обращения к Hugging Face Hub во время работы.
